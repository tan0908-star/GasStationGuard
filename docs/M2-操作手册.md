## 一、⚠️ 本轮最关键的发现：int8 量化差点让模型完全失效

这是本轮最有价值的部分，请务必理解，因为它解释了"为什么模型要那样导出"。

### 现象

第一次导出的 int8 模型，**编译、加载、运行全部正常，不报任何错**，但：

```
框参数范围 [0.0, 656.4]    ← 正常
类别分数范围 [0.000, 0.000]  ← 全部是 0
```

**一张图都检不出来。而且没有任何报错。**

这正是项目章程里明令禁止的**静默失效** —— 如果不做端到端验证，这个模型会一路带到 M3，
真机夜测时表现为"车来了不报警"，而我们可能要花几天去怀疑相机、怀疑阈值、怀疑光照。

### 根因

YOLOv8 的最终输出是把两样东西拼在一起：

```
cat([ 框参数(值域 0~640),  类别分数(值域 0~1) ], dim=1)  →  [1, 84, 8400]
```

int8 量化会根据标定数据，给这**一整个张量**计算**一个**缩放系数（per-tensor）。  
标定时观测到的值域是 **0~656**（被框参数撑大的），于是：

```
scale = 656 / 255 ≈ 2.57
```

结果所有 0~1 的类别分数在量化时全部被抹平：

```
0.9 / 2.57 = 0.35  →  round →  0  →  反量化回来还是 0
```

**分数全变 0，模型彻底失效，而且不报错。**

### 修复

在 ONNX 图里，于 concat 之前给**框分支除以 640**，把两个分支的值域都拉到 0~1：

```
cat([ 框/640(0~1),  类别分数(0~1) ], dim=1)
```

这样单一 `scale ≈ 1/255` 就能同时精确表示两者：

| | 修复前 | 修复后 |
|---|---|---|
| 输出量化 scale | 2.5743 | **0.00402** |
| 值域 | 0 ~ 656 | **0 ~ 1.03** |
| 框精度 | — | ≈ 2.5 像素（640 空间的 0.4%） |
| 分数精度 | **完全丢失** | ≈ 0.4% |

**代价**：模型吐出的框坐标变成**归一化的 0~1** 而不是像素值。  
安卓端 `YoloDetector.kt` 里必须相应**乘以 inputSize**，两边必须一起改，否则框会整体错位。
代码里那一段有醒目的 ⚠️ 标注。

## 二、模型是怎么来的（可复现）

导出脚本：`tools/export_yolo_tflite.py`（三步管线）

```
① yolov8n.pt  --(ultralytics / torch.onnx)-->       yolov8n.onnx
①′ yolov8n.onnx --(插入 Div(640) 修复量化)-->        yolov8n_normalized.onnx
② ...normalized.onnx --(onnx2tf)-->                 SavedModel (float32)
③ SavedModel --(tf.lite.TFLiteConverter + 标定)-->  app/src/main/assets/yolo_int8.tflite
```

### 为什么不用 ultralytics 自带的 tflite 导出

实测（2026-10，Windows）：

| 版本 | 结果 |
|---|---|
| ultralytics 8.4.170 | `format='tflite'` 被 LiteRT 取代，源码里硬断言 **"only supported on Linux x86 and macOS"** |
| ultralytics 8.3.253 | `export_tflite()` 是**空壳**，只算了个路径就返回（源码挂着 `# BUG .../issues/13436`） |

两条路都走不通，所以改成自己控制的三步管线。

### 关于 int8 标定集（对夜间识别很重要）

int8 量化需要一批"代表性图片"统计每层激活值的范围。  
**只用白天图片标定，量化区间会偏向白天**，夜里画面整体偏暗时量化误差变大。

本脚本的标定集 = **COCO128 原图 + 同一批图 gamma 压暗版**（`tools/export_yolo_tflite.py`
里的 `build_representative_dataset`），让量化区间同时覆盖白天和夜间。

> ⚠️ **这只是权宜之计。等 M5 能录下真实现场的夜间画面后，应该用真实现场夜拍图重新标定一次。**
> 这是提升夜间识别率最划算的一步，成本只是重跑一次导出脚本。

### 在电脑上验证模型（不用手机）

```bash
.venv/Scripts/python.exe tools/verify_tflite.py \
    --dir datasets/coco128/images/train2017 --count 40
```

它会用**和安卓端完全一样**的算法（letterbox → 量化 → 推理 → 反量化 → 解码 → NMS）跑一遍，
打印检出的类别和置信度。换模型后**务必先跑这个再上真机**。

## 四、坐标映射原理（出问题时看这里）

框画在正确位置，要经过**两级**坐标换算，任何一级算错框都会偏：

```
第一级（在 YoloDetector.kt 里）：
  模型输出: 640×640 输入图里的框（已归一化 0~1）
     ↓ 反 letterbox：减掉灰边偏移、除以缩放比、再除以原图尺寸
  归一化坐标（0~1，相对【摆正后】的原图）

第二级（在 DetectionOverlayView.kt 里）：
  归一化坐标
     ↓ fitCenter 规则：scale = min(视图宽/画面宽, 视图高/画面高)
     ↓ 再乘以显示宽高、加上居中偏移（也就是两边黑边的宽度）
  屏幕像素坐标
```

**如果框整体偏向一边** → 黑边偏移算错了（第二级）。
**如果框整体偏小或偏大** → letterbox 的缩放/偏移算错了（第一级）。
**如果框转了 90°** → 相机旋转方向搞反了（`imageProxy.imageInfo.rotationDegrees` 的用法）。

## 五、常见问题排查

### 问题 1：诊断条显示「模型加载中…」一直不变

**原因**：`app/src/main/assets/yolo_int8.tflite` 没打进 APK，或者加载抛异常（会有红字）。

**检查**：
1. 确认文件存在：`app/src/main/assets/yolo_int8.tflite`（约 3.25 MB）
2. 确认 `app/build.gradle.kts` 里有 `androidResources { noCompress += "tflite" }`
   —— **没有这一行，TFLite 会因为 assets 被压缩而加载失败**
3. **Build → Clean Project → Rebuild Project**

### 问题 2：诊断条有识别耗时，但永远「无目标」

按顺序排查：
1. 镜头前确实没有车？把手机对着手机相册里的汽车照片试试
2. **置信度阈值**：当前是 `0.35`。夜间或远距离可能不够，可临时调到 `0.25`
   （在 `YoloDetector.kt` 的 `CONF_THRESHOLD`）
3. **模型本身坏了**：在电脑上跑 `tools/verify_tflite.py` 确认模型能检出车

### 问题 3：框能出来，但位置明显不对

见上面第四节的两级坐标映射。**先看第 4 项白框对齐不对齐**，那能立刻区分是哪一级的问题。
把截图发我。

### 问题 4：App 变卡 / 手机发烫

推理是 2 fps，正常不该卡。如果卡：
1. 看诊断条里的毫秒数。超过 500ms 说明模型跑得太慢，会拖累帧率
2. 临时把 `DETECT_INTERVAL_MS` 从 500 调到 1000（1 fps）
3. M6 会做完整的温控与自适应帧率

### 问题 5：编译报 `Namespace 'com.google.ai.edge.litert' is used in multiple modules`

**这是 LiteRT 2.x 的已知打包问题**（它拆成了 `litert` 和 `litert-api` 两个模块，
却声明了同一个 namespace，AGP 清单合并直接拒绝）。

**解决**：`gradle/libs.versions.toml` 里的 `litert` 必须是 **`1.4.2`**，不要升级到 2.x。

## 七、已知限制与下一步

### 已知限制

1. **没在真机验证过**（手机掉线）。上面的清单必须走一遍。
2. **COCO 预训练模型对夜间可能不够好**。COCO 里几乎没有夜间加油站场景，
   这是目前最大的准确率风险。缓解手段按性价比排序：
   - 用真实夜拍图重新标定 int8（成本最低，先做这个）
   - 加大输入尺寸到 896（更慢）
   - M5 之后收集真实样本做微调（最有效，但要标注）
3. **长曝光拖影**（M1 留下的取舍）会同时影响识别和肉眼观察。
4. **APK 30MB**：包含了 4 个 CPU 架构的原生库，真机只需要 arm64。
   可以加 `abiFilters` 砍到约 12MB（非必需）。

### 下一步（M3）

ROI 监测区域 + 多帧确认 + 强制报警（全屏红闪 + 铃声 + 震动 + TTS + 长按 2 秒解除 + 30 秒未解除自动拨号）。

**但在开始 M3 之前，请先完成上面的真机验证清单** —— 尤其是第 4、5、6 项。
M3 的整个报警逻辑都建立在"框是准的"这个前提上。
